# 编队智能布置模块开发路线与首阶段计划

日期：2026-10-12。阶段一已开发并验证完成；其余阶段仍为计划，尚未实施。

**目标：** 从文字、语音或图像得到结构化布置需求，经过约束校验生成静态场景；用户调整单个单位的位置与朝向后，保存并复用方案，逐步积累可用于模型适配的样本。

**依据：** 用户提供的十项功能图片 `C:/Users/ANDY/Desktop/24ffc6ad4a5d4d7a3537088b5c0a769f.png`、当前 `TacticalDemo/Source/TacticalDemo/ScenarioConfig.h` 与 `PROJECT_STATUS.md`。图片是目标能力清单，不表示这些功能已经实现。当前实现情况依据代码和项目记录，规划时未重新运行验证；阶段一实施后已完成 UE 编译、16项回归、本地 Qwen 和跨地图重启恢复验证，详见 PROJECT_STATUS.md。

**架构：** 各输入方式统一转换成布置需求；C++ 负责资源检查、几何布置、约束验证与场景应用。聊天和人工编辑共用同一份当前场景状态。场景快照、历史方案、训练样本分别管理。

**技术基础：** UE5.3、C++、UMG、本地 Qwen 文本接口、JSON；语音和视觉组件待分别验证本机运行条件后接入。

## 全局约束

- 单位保持静止，不增加自动飞行、自动运动或弹道仿真。
- 不恢复聊天修改颜色；保留已登记贴图切换。
- 保留手动应用及简短说明，不恢复原始候选 JSON 的聊天展示。
- 保持旧配置可加载；失败、取消或无效资源不能破坏当前场景。
- 先复用已有 J20、J10、机场与基础占位模型，不以新增模型库为前置条件。
- 原地图中的布景与系统管理的单位应有明确边界，默认仅操作系统管理单位。

- [ ] 在配置窗口编辑并显示区域，保存到方案。单位占地范围取模型边界及安全余量，不能只比较中心点。
- [ ] 将同一约束校验用于聊天生成、手动拖动和历史方案加载；明确违规预览、拒绝应用及错误定位。

**验收：** 用户配置的区域和间距在不同操作入口一致生效，能指出具体违规单位和原因。

## 阶段三：完整文字需求与 AI 批量布置

对应图片第 1、6 项。

- [ ] 让 Qwen 提取单位型号、数量、阵营、区域、坐标/高度及通用排列需求，输出统一的结构化布置请求。
- [ ] C++ 根据请求与约束计算位置和朝向；资源和几何检查通过后生成逐单位 JSON，避免将空间计算完全交给语言模型。
- [ ] 支持多个编组一次生成；简短说明结果，点击应用后整体更新，再进入人工编辑。
- [ ] 建立固定语句验收集，检查数量、型号、区域、位置和朝向；包含歧义、无效资源、不可行布置及取消请求。

**验收：** 同一文字需求可以生成满足约束的静态布置；不可行时明确说明原因；拖动修改后可以保存并复用。

**验收：** 在未参与训练的样本上有可复现改进。保存历史方案本身不代表已经微调模型。

## 顺序与里程碑

1. 可编辑、可保存、可复用：先把现有飞机和地图做成可靠的静态布置工具。
2. 可约束、可批量生成：形成文字驱动 AI 布置的完整流程。
3. 可多模态输入：加入语音与指定类型图像，共用已有场景核心。
4. 可积累和利用样本：完成评测，再决定领域适配方式。

语音与图像组件可以在核心流程稳定后分别验证；不建议一开始同时改动所有输入方式。完整工期应在第一阶段验证数据迁移、拖动交互，并完成本机语音/视觉小试后估算；当前不承诺固定完成日期。
